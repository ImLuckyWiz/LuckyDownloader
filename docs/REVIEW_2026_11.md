## 1. Executive Summary

LuckyDownloader has a clean modular core (`core/`), a well-structured pure-JS Premiere CEP timeline engine (`premiere-plugin-cep/src/`), strong bilingual i18n tooling (`tools/i18n.py`), and a fast, comprehensive test suite (**1,752 Python tests + 134 CEP tests passing**).
However, rapid feature expansion in Phases 1–9 (parallel queue, multi-provider support, playlist archives, watchlist, and the LuckyTwitch → LuckyDownloader rebrand) introduced **13 High-severity** and **27 Medium-severity** bugs and security risks (0 Critical).
The biggest operational risks are: (1) **broken feature wiring** where `check_all_watchers()` never persists watchlist state (`G-01`) and playlist `--download-archive` is dead code (`A-03`); (2) **parallel-queue hazards** where same-video jobs share one work folder and delete each other's files (`A-01`), closing the window only cancels 1 of N active workers (`D-01`), and `QueueTab` leaks O(N²) signal connections (`D-02`); (3) **security & upgrade bugs** including shipping `.debug` + `--enable-nodejs` on port 8099 in the Premiere CEP release (`F-01`), auto-executing `yt-dlp` on `luckydownloader://` deep links (`C-01`), raw extractor IDs in `shutil.rmtree` workdir paths (`A-02`), and `installer.iss` reusing the legacy `AppId` without `UsePreviousAppDir=no`, causing upgrades to install into `%LOCALAPPDATA%\Programs\LuckyTwitch` (`I-02`).
Nearly all High-priority findings are localized and small (`Effort: S`), making a focused stabilization pass fast and low-risk.

### [A-01] Parallel jobs for the same video share one work folder and delete each other's files
- **Severity:** High
- **Type:** Bug / Reliability
- **Confidence:** Verified (by reading the code)
- **Where:** `core/finalize.py:580-583` (`workdir = out_dir / f".luckytwitch_{id}_{format_id}"`), `core/download.py:455-458` and `:671-674` (`shutil.rmtree(pdir)` for `part{index}`), `core/finalize.py:699` (`shutil.rmtree(workdir)`), `qt_ui/queue_runner.py:82-119` (up to 4 workers), `qt_ui/main_window.py` clip enqueue loop around `:1343` (one `Job` per clip, same source).
- **What's wrong:** The work folder name depends only on the video id and format. Two queue items for the same VOD (very common: "Add N clips to queue", or two cut lists of one VOD) get the **same** folder. Each single-clip job has exactly one part, so both use `part1/`. With "parallel jobs" set to 2-4:
  - job B's `download_section*` runs `shutil.rmtree(workdir/"part1")` while job A is still writing into it;
  - whichever job finishes first runs `shutil.rmtree(workdir, ignore_errors=True)` and removes the other job's in-progress files;
  - with the `full` strategy both run `yt-dlp --continue -o full.%(ext)s` into the same file at the same time.
- **Why it matters:** Random "Part 1 came out empty", ffmpeg "No such file" errors, or a corrupt full download. It only shows up with parallel jobs, so it looks flaky and is hard to report.
- **Suggested fix:** Make the work folder unique per job and keep resume working for the same job:
  ```python
  # finalize.py
  job_key = hashlib.sha1(f"{src.url}|{opts.cut_text}|{job.single_clip and job.single_clip.get('id')}".encode()).hexdigest()[:10]
  workdir = out_dir / f".ld_{_safe_id(src)}_{fmt_tag}_{job_key}"
  ```
  As a second guard, keep a module-level `set` of active work folders under a lock and refuse (or wait) when a second job would take the same one. Add a test that runs two fake jobs for the same VOD with `max_concurrent=2` and checks that both results exist.
- **Effort:** S

### [A-02] Work folder path built from the raw extractor id: path traversal and a recursive delete outside the output folder
- **Severity:** High
- **Type:** Security / Bug
- **Confidence:** Likely (code path verified; whether a given yt-dlp extractor returns `/`, `..` or `:` in `id` needs a live check)
- **Where:** `core/source_info.py:561` (`id=str(info.get("id", ""))`, no cleaning), `core/finalize.py:580-583` (id goes into a path), `core/finalize.py:699` (`shutil.rmtree(workdir, ignore_errors=True)`), `core/playlist.py:93` (`id=item.id` from flat playlist entries).
- **What's wrong:** For non-Twitch sources `src.id` is whatever yt-dlp reports. yt-dlp's generic extractor derives the id from the URL with `urllib.parse.unquote(basename)`, so a URL like `https://host/..%2F..%2F..%2FSomeFolder.mp4` can produce an id that contains `../`. The work folder is `out_dir / ".luckytwitch_<id>_..."`, created with `mkdir(parents=True)`, filled by yt-dlp, and finally removed with `rmtree(..., ignore_errors=True)`. Even without bad intent, ids with `:`, `?`, `*`, `|` or a trailing dot fail on Windows (`:` even creates an NTFS alternate data stream). The final file names are safe because they go through `safe_name`; the work folder name does not.
- **Why it matters:** A link (including a `luckydownloader://` link, which runs «Get info» on its own, see C-03) can point the app at a crafted URL; once the person presses Download, files are written to and then recursively **deleted** from a folder outside the output folder.
- **Suggested fix:** Never use a remote id in a path without cleaning:
  ```python
  def _safe_id(src) -> str:
      raw = src.twitch_vod_id or src.id or ""
      cleaned = re.sub(r"[^A-Za-z0-9_-]", "_", raw)[:40]
      return cleaned or hashlib.sha1(src.url.encode()).hexdigest()[:12]
  ```
  Also check `workdir.resolve().is_relative_to(out_dir.resolve())` before `mkdir` and before `rmtree`. Add tests with ids `"../../x"`, `"a:b"`, `"CON"`, `""`.
- **Effort:** S

### [A-04] Cancel that arrives while the process is starting is ignored until the download finishes
- **Severity:** Medium
- **Type:** Bug / Reliability
- **Confidence:** Verified (by reading)
- **Where:** `core/download.py:342-358` (`run_ytdlp`), `:155-167` (`run_ffmpeg`), `core/chat.py:100-108`; `core/runtime.py:165-169` (`Ctx.cancel` only kills `self.proc` if it is already set).

### [C-01] `luckydownloader://` deep-link handler automatically runs `yt-dlp` on untrusted URLs (with cookies if configured) and allows SSRF via DNS or integer IPs
- **Severity:** High
- **Type:** Security / Privacy
- **Confidence:** Verified
- **Where:** `qt_ui/main_window.py:1385-1416` (`open_link` calls `self.on_get_info()` immediately at line 1415), `weblink.py:67-78` (`_blocked_host`), `core/source_info.py:194-204` (`get_source_info` passes `--cookies-from-browser`).
- **What's wrong:**
  1. `weblink.py:6-7` claims *"A link only fills in the form... the person still checks the cut points and presses the button."* In reality, `open_link` calls `self.on_get_info()` automatically without user confirmation.   2. If the user has browser cookies enabled (`cookies_from_browser`), `get_source_info` automatically attaches `--cookies-from-browser` if `url` is in `DEFAULT_COOKIE_DOMAINS` (or for **any** site if `cookies_scope == "all"` or if `url` redirects from an eligible domain/subdomain).

## L. Product and feature ideas

### [L-01] Pre-flight disk-space check before starting full-VOD or multi-part downloads
- **Severity:** Low
- **Type:** Idea (Robustness / UX)
- **Confidence:** Verified
- **Where:** `core/finalize.py:216` (`run_job`), `core/source_info.py:137` (`estimate_bytes`), `qt_ui/main_window.py`.
- **What's wrong:** `core/source_info.py:137` already computes `estimate_bytes(duration, fmt)` for the Plan tab preview, and `core/chat.py:126` notes that ProRes 4444 chat overlays can reach ~28 GB/hour. Furthermore, when strategy is `"full"` (`keep_full=False`), `run_job()` needs enough free disk space on the output drive for **both** the temporary full VOD (`_full_<pid>_<id>/full.mp4`, up to 15–30 GB for a 6-hour 1080p60 stream) **and** the split output parts simultaneously before `shutil.rmtree(workdir)` runs in `finally`. Currently, `shutil.disk_usage(out_dir)` is never checked before starting or queuing a job.
- **Why it matters:** A multi-hour VOD download fails 90% of the way through (during `split_copy` or `chatrender`) with an opaque `ffmpeg`/`yt-dlp` I/O error when the target drive runs out of space.
- **Suggested fix:** Compare `shutil.disk_usage(out_dir).free` against the estimated bytes (multiplying by `1 + kept_fraction` when `strategy == "full"`) before starting a job, and show a warning dialog or banner if free space is below `estimated_bytes * 1.15`.
- **Effort:** S

### [L-02] Persist waiting/interrupted queue items to `luckytwitch_queue.json` for crash and update recovery
- **Severity:** Low
- **Type:** Idea (Reliability / UX)
- **Confidence:** Verified
- **Where:** `qt_ui/queue_model.py`, `qt_ui/main_window.py`, `core/job.py`.
- **What's wrong:** `QueueModel.items` lives purely in memory. If the user queues 20 videos (or a 50-item playlist), or applies an in-app update (`UpdateDialog` -> `launch_installer` with `/CLOSEAPPLICATIONS`), or the app crashes, all `queued`, `running`, and `failed` jobs in the queue are lost on exit.
- **Why it matters:** Users queuing batch downloads or playlists lose their entire queue when restarting or updating the app.
- **Suggested fix:** Serialize `Job` (`SourceInfo`, `Plan`, `JobOptions`, `Clip`) and `QueueItem` status (`queued` / `failed` / `cancelled`, resetting `running` to `queued` on startup) to `DATA_DIR / "luckydownloader_queue.json"` via `atomic_write_json` whenever items are added, finished, or removed.
- **Effort:** M

### [L-03] One-click "Export Diagnostics Bundle" in Options / Log drawer for bug reports
- **Severity:** Low
- **Type:** Idea (Supportability / UX)
- **Confidence:** Verified
- **Where:** `qt_ui/tabs/queue.py`, `qt_ui/tabs/options.py`, `core/tools.py:describe_tools`.
- **What's wrong:** When a download fails due to a site extractor change, ffmpeg error, or tool setup issue, users must manually copy the log text and separately look up their OS, app version, `yt-dlp` version, `ffmpeg` path, and active settings (while remembering not to leak `config.json` tokens or cookies).

- **Effort:** S

### [L-04] Deterministic deterministic-ID temp folders + `--continue` resume for interrupted single-stream and full-VOD downloads
- **Severity:** Low
- **Type:** Idea (Robustness / Performance)
- **Confidence:** Verified
- **Where:** `core/finalize.py:251`, `core/download.py:372`.
- **What's wrong:** Currently (`A-06`), `run_job()` names its temporary workdir `_full_{os.getpid()}_{id(ctx)}`. Because `os.getpid()` and `id(ctx)` change on every run (and even on **"Retry"** within the same session!), `yt-dlp`'s `.part` file from an interrupted 20 GB VOD download can never be resumed—pressing **"Retry"** in the Queue tab deletes nothing (leaving the old `_full_*` directory orphaned) and starts downloading from `0%` in a brand-new `_full_*` directory.
- **Why it matters:** A brief network drop or user pause/cancel at 85% of a 20 GB VOD forces re-downloading all 20 GB from scratch on Retry.
- **Suggested fix:** Key the workdir deterministically by a hash of `(src.provider, src.id or src.url, opts.quality, part_spans)` (e.g. `.luckydownloader_tmp_<hash12>`), keep `.part` files when a job fails with a network error or is paused, pass `--continue` to `yt-dlp`, and clean up the deterministic workdir only on completion or explicit **"Remove from queue"**.
- **Effort:** M

### [L-05] Decouple `core/` from `sys.modules.get("luckytwitch_engine")` via a clean `ToolRunner` / dependency object
- **Severity:** Low
- **Type:** Idea (Architecture / Maintainability)
- **Confidence:** Verified
- **Where:** `core/download.py`, `core/finalize.py`, `core/chat.py`, `core/muted.py`, `luckytwitch_engine.py`.
- **What's wrong:** Seventeen functions across `core/download.py`, `core/finalize.py`, `core/chat.py`, and `core/muted.py` contain boilerplate like:
  ```python
  eng = sys.modules.get("luckytwitch_engine")
  _find = getattr(eng, "find_tool", find_tool) if eng else find_tool
  ```
  solely so legacy tests that do `monkeypatch.setattr(eng, "find_tool", ...)` keep working after `luckytwitch_engine.py` was split into `core/*` in v2.5.0.
- **Why it matters:** Every new function in `core/` has to remember which symbols tests might monkeypatch on `luckytwitch_engine` (missing one causes subtle test-vs-production divergence).
- **Suggested fix:** Gradually migrate tests to patch the canonical `core.<module>` symbols (or pass a lightweight `RuntimeDeps` object on `Ctx`), then retire the `sys.modules.get("luckytwitch_engine")` indirection.
- **Effort:** M
