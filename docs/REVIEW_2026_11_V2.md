## 1. Executive Summary

At HEAD `4fb1877`, LuckyDownloader has matured substantially since the `953fedc` V1 baseline: **all 1,857 Python tests pass with zero skips**, **all 134 CEP Node tests pass**, **`tools/i18n.py check` passes with 806 messages / 829 Spanish translations and 0 unwrapped UI literals**, macOS `ffmpeg`/`ffprobe` and `ZXPSignCmd` downloads now enforce SHA-256 checksums, `MainWindow`/`PlanTab`/`Timeline` were cleanly decomposed into smaller modules, atomic JSON helpers were introduced, and Qt UI + security hardening resolved or partially resolved most V1 blockers.

At the same time, this independent V2 audit surfaced **63 findings** (**0 Critical, 10 High, 30 Medium, 20 Low, 3 Nit**) across 12 areas (`A`–`K`, plus new surface `M` for the headless CLI and root Colab scripts). Three clusters account for the highest user impact:

1. **Broken or regressed V1 fixes:** Several fixes landed after `953fedc` have subtle wiring bugs that neutralize them in production:
   - `_save_ui_state()` (`qt_ui/session_persistence.py:195-214`) constructs a fresh `UIState` without `max_concurrent_jobs`, `rate_limit`, `log_open`, or `splitter_sizes`, silently resetting user queue settings on every app exit (`G-01`).
   - `split_rate_limit()` is applied **twice**—once in `QueueTab.start_queue` and again in `QueueRunner.worker_loop`—dividing parallel download speed by `concurrency²` (`D-01`) while mutating `opts.rate_limit` in-place (`A-07`).
   - `workdir / ".running"` is never removed in a `finally:` block on failure/cancellation, defeating both `--continue` download resume and `cleanup_stale_workdirs()` (`A-01`).
   - `resolve_cookies_for_request()` filters `yt-dlp -J` metadata fetches but was never wired into `run_job()`, leaking browser cookies to Twitch and arbitrary hosts during downloads (`C-01`).
   - `check_disk_space()` in `run_job()` only checks `fmt.filesize` (`0` on 100% of Twitch VODs) instead of calling `estimate_bytes()` (`A-03`).
2. **Premiere CEP plugin regressions (`F-01`, `F-02`):** Fixing DOM XSS broke `#limitChapter` completely (`runner.js:890` omits `parsed: fr.parsed`, plus chapter-edge cuts abort as `"uncertain"` and verification checks un-scoped totals), while wiring `preferences` into `applyFilePreferences()` pads every clip **twice** (`2 × pad_before`, `2 × pad_after`) because `core/chapters.py` already bakes padding into `.markers.json` timestamps.
3. **New headless CLI & root Colab scripts (`M-01`..`M-05`, `I-01`..`I-02`):** Five root Colab scripts hardcode personal Google Drive paths, VOD URLs, and 22 Zelda timestamps while running `git reset --hard origin/main`; `colab_job.sh` moves only `*.mp4` and runs `rm -rf /tmp/* /root/.cache/*`; `cli.py --chapters` silently skips Twitch chapters because `job.client` is `None`; and `.github/workflows/build.yml` creates a public `Latest` GitHub Release before artifacts or `SHA256SUMS.txt` exist.

### [A-01] `.running` lock file is never removed when `run_job()` fails or is cancelled, breaking both download resume (old `L-04`) and stale-workdir cleanup (old `A-08`)
- **Severity:** High
- **Type:** Bug / Reliability
- **Confidence:** Confirmed
- **Where:** `core/finalize.py:122-161` (`compute_job_workdir`, `cleanup_stale_workdirs`), `core/finalize.py:738-747` (`.running` creation), `core/finalize.py:897-902` (unlink only on normal completion).
- **What's wrong:**
  1. `run_job()` writes `lock_file = workdir / ".running"` at `core/finalize.py:743-745`, but only removes `lock_file` at lines `899-900` inside the success path—**not** inside a `finally:` block. Whenever a job raises `EngineError` or `Cancelled`, `run_job()` exits early and leaves `.running` on disk permanently.
  2. When the user clicks **Retry** on a failed or cancelled job (or resumes in a later session), `run_job()` computes the deterministic `workdir`, checks `if (workdir / ".running").exists():` (`core/finalize.py:739`), assumes another active worker owns it, and diverts the retry into a brand-new `f"{workdir.name}_{os.getpid()}_{uuid.uuid4().hex[:6]}"` directory—**completely defeating `--continue` resume** and restarting the download from 0%.
  3. Worse, `cleanup_stale_workdirs()` (`core/finalize.py:153-154`) unconditionally skips any directory where `(entry / ".running").exists()` without verifying whether the recorded PID is still alive. Consequently, **no failed or cancelled workdir is ever deleted by cleanup**, even when the user clicks «Clean temporary files» (`max_age_hours=0.0`) in Options.
  4. In addition, `compute_job_workdir()` (`core/finalize.py:127-131`) omits `job.single_clip` from its hash tuple, and checking `.exists()` before `mkdir()`/`write_text()` is non-atomic across concurrent workers.
- **Why it matters:** Interrupted multi-gigabyte VOD downloads cannot resume partial fragments on retry, and failed/cancelled temporary folders accumulate indefinitely on the user's drive.
- **Suggested fix:** Acquire `.running` atomically with `os.open(..., os.O_CREAT | os.O_EXCL | os.O_WRONLY)`, always remove `lock_file` in a `finally:` block in `run_job()`, include `single_clip` in `compute_job_workdir()`, and treat `.running` locks as stale in `cleanup_stale_workdirs()` when `max_age_hours <= 0` or the PID is dead:
  ```python
  # core/finalize.py — inside run_job()
  workdir = compute_job_workdir(src, opts, fmt=fmt, out_dir=out_dir, single_clip=job.single_clip)
  if not workdir.resolve().is_relative_to(out_dir.resolve()):
      raise EngineError(t("Unsafe work directory path"))
  workdir.mkdir(parents=True, exist_ok=True)
  lock_file = workdir / ".running"
  try:
      fd = os.open(str(lock_file), os.O_CREAT | os.O_EXCL | os.O_WRONLY)
      os.write(fd, str(os.getpid()).encode("utf-8"))
      os.close(fd)
  except FileExistsError:
      import uuid
      workdir = workdir.with_name(f"{workdir.name}_{os.getpid()}_{uuid.uuid4().hex[:6]}")
      workdir.mkdir(parents=True, exist_ok=True)
      lock_file = workdir / ".running"
      lock_file.write_text(str(os.getpid()), encoding="utf-8")

  try:
      # ... download / split / finish body ...
      shutil.rmtree(workdir, ignore_errors=True)
  finally:
      try:
          lock_file.unlink(missing_ok=True)
      except OSError:
          pass
  ```
- **Effort:** S

### [A-02] Cutting a source with unknown duration (`src.duration == 0.0`) forces `"full"` strategy and drops all `part.end` boundaries in `split_copy()`
- **Severity:** High
- **Type:** Bug
- **Confidence:** Confirmed
- **Where:** `core/finalize.py:510-514` (`split_copy`), `core/planning.py:95-99` (`choose_strategy`), `core/finalize.py:851` (`run_job`).
- **What's wrong:**
  - When an extractor reports unknown duration (`src.duration == 0.0`, `core/source_info.py:680`) and the user enters explicit cut points (e.g., `"0:00 - 1:00"` or `"0:10 - 1:00"`):
    1. `choose_strategy(parts, duration=0.0, mode="auto")` (`core/planning.py:95`) computes `coverage = (sum(...) / duration) if duration else 1.0`, which evaluates to `1.0 >= 0.6` and forces `strategy = "full"` instead of `"sections"`.
    2. `run_job()` downloads the entire stream and calls `split_copy(ctx, full, plan.parts, src.duration, ...)` (`core/finalize.py:851`) with `duration = 0.0`.
    3. Inside `split_copy()` (`core/finalize.py:510`):
       ```python
       boundaries = sorted({0.0} | {p.start for p in parts} | {p.end for p in parts if p.end < duration - 0.5})
       ```
       Because `duration == 0.0`, `duration - 0.5` is `-0.5`. Every `p.end > 0` fails `p.end < -0.5`, so **all `p.end` boundaries are discarded**:
       - `"0:00 - 1:00"` produces `boundaries = [0.0]`, returning `{1: (full, 0.0, 0.0)}` — saving the **entire uncut video** without invoking `ffmpeg`.
       - `"0:10 - 1:00"` produces `boundaries = [0.0, 10.0]`, keeping everything from `0:10` to EOF.
- **Why it matters:** While old `A-10` allowed `parse_cut_points()` to accept `duration == 0.0`, trimming those videos still silently fails at split time and outputs uncut or tail-untrimmed video files.
- **Suggested fix:** Default `"auto"` strategy to `"sections"` when `not duration or duration <= 0`, and only filter `p.end < duration - 0.5` in `split_copy()` when `duration and duration > 0`:
  ```python
  # core/planning.py:95-99
  if not duration or duration <= 0:
      return (mode if mode in ("full", "sections") else "sections"), 1.0

  # core/finalize.py:510
  end_points = {p.end for p in parts if (not duration or duration <= 0 or p.end < duration - 0.5)}
  boundaries = sorted({0.0} | {p.start for p in parts} | end_points)
  ```
- **Effort:** S

### [A-03] Pre-flight disk-space check (`check_disk_space`) only checks 200 MB for all Twitch VODs because `fmt.filesize` is `0` and `estimate_bytes()` is never called
- **Severity:** Medium
- **Type:** Bug / Reliability
- **Confidence:** Confirmed
- **Where:** `core/finalize.py:731-736` (`run_job`), `core/source_info.py:457-507` (`parse_formats`), `core/source_info.py:853-857` (`estimate_bytes`).
- **What's wrong:**
  1. `run_job()` (`core/finalize.py:731-736`) computes `required_bytes` solely from `getattr(fmt, "filesize", 0) or 0`, falling back to `200 * 1024 * 1024` (200 MB) whenever `filesize == 0`.
  2. `parse_formats()` (`core/source_info.py:496-504`) — used for **all Twitch VODs** — never populates `filesize` on `VideoFormat` (only `tbr`, leaving `filesize=0`), and `run_job()` never calls `estimate_bytes(fmt, dl_seconds)`.
  3. As a result, a 10-hour 1080p60 Twitch VOD (~40 GB needed) only checks for 200 MB free space. Moreover, for `"sections"` mode, checking the full stream size instead of `sum(p.duration for p in plan.parts)` can false-positive on small clips, and `stream_dir(src, opts)` is not checked when `provider_out_dirs` points to a different drive than `opts.out_dir`.
- **Why it matters:** Old `L-01` does not catch low-disk-space failures before downloading large Twitch VODs, causing `ffmpeg` or `yt-dlp` to fail hours into a download.
- **Suggested fix:** Fall back to `estimate_bytes(fmt, dl_seconds)` when `fmt.filesize <= 0`, scale by section ratio when `plan.strategy == "sections"`, and also check the resolved final directory (`stream_dir(src, opts)`).
  ```python
  # core/finalize.py:731-738
  from core.source_info import estimate_bytes
  dl_seconds = (src.duration or 0.0) if plan.strategy == "full" else sum(p.duration for p in plan.parts)
  filesize = getattr(fmt, "filesize", 0) or 0
  if filesize > 0 and plan.strategy != "full" and src.duration and src.duration > 0:
      filesize = int(filesize * min(1.0, dl_seconds / src.duration))
  if filesize <= 0:
      filesize = estimate_bytes(fmt, dl_seconds)
  multiplier = 2.1 if (plan.strategy == "full" and (len(plan.parts) > 1 or opts.exact)) else 1.1
  required_bytes = max(200 * 1024 * 1024, int(filesize * multiplier)) if filesize > 0 else 200 * 1024 * 1024
  check_disk_space(out_dir, required_bytes)
  ```
- **Effort:** S
